# EXT4 Forensics Workbench — Backend v0.5.2

FastAPI backend for an academic EXT4 deleted-file examination workbench. Existing scans use the local filesystem parser and SQLite casebook; report narrative generation is optionally assisted by Groq.

## Start (Windows PowerShell)

```powershell
cd backend
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
# Add GROQ_API_KEY to .env to enable Groq report writing.
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

## Start (Linux / macOS)

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
# Add GROQ_API_KEY to .env to enable Groq report writing.
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

API documentation is available at `http://127.0.0.1:8000/docs`. The frontend's `VITE_API_BASE` can override the default API URL.

## DOCX report layout (v0.5.2)

DOCX exports use A4 portrait layout, page headers/footers, stylized findings tables, and an embedded diagram of timestamped activity-log events. The method section explains the actual read-only scanning and recovery implementation, including SHA-256 integrity checks, EXT4 inode/directory parsing, artifact timeline extraction, retained-block recovery, signature identification, and recovered-output validation. Install `Pillow` from `requirements.txt` to render the timeline graphic.

## Report generation and Groq

- Set `GROQ_API_KEY` in `backend/.env`; the key is read by the backend and is never sent to the browser.
- `GROQ_MODEL` defaults to `openai/gpt-oss-20b`. Set it to a model available to your Groq account if needed.
- `GROQ_TIMEOUT_SECONDS` defaults to 60.
- The model receives structured case/evidence metadata and a bounded summary of filesystem findings, timelines, hashes, and artifact metadata. The disk image bytes and raw artifact-content bodies are not sent.
- The narrative is cached by a SHA-256 digest of its structured input to avoid repeated API calls for an unchanged report.
- Without a key, or if Groq is unavailable, report generation still succeeds with a labelled local fallback. The report metadata states whether the narrative was generated by Groq or the fallback was used.
- Review all model-written text against the underlying evidence before using the report for legal, disciplinary, or incident-response decisions. The model is not a substitute for examiner review.

## Intake and schema upgrades

The UI captures a case number/title plus evidence item/type, image path, optional evidence description, and optional source-device identifiers. The generated JSON/DOCX reports use a whitelist for case/evidence header fields, so legacy administrative, incident-context, acquisition, receipt, custody, and storage metadata already present in SQLite is not exposed in the report. SQLite retains existing columns for backward compatibility.

## Existing forensic features

- SHA-256 before/after evidence-image verification
- Local SQLite casebook and append-only chained JSONL integrity ledger
- EXT4 superblock, group descriptor, inode, deleted directory-entry, and slack heuristic analysis
- Targeted JBD2 journal inspection and pytsk3 filesystem cross-check
- Deleted-file recovery, signature identification, validation, and recovered-file hashes
- Targeted artifact extraction and timeline building
- DOCX and JSON forensic report exports

## Scope and limitations

This is an academic capstone implementation, not a validated commercial forensic product. Journal handling extracts evidence and correlations; it does not replay every JBD2 transaction. Preserve originals and independently validate results using your laboratory's approved procedures.
